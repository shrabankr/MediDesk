# MediDesk Security Rules & Threat Mitigation Guidelines

This document outlines mandatory security principles, cryptographic standards, and threat prevention rules across all MediDesk subsystems.

---

## 1. Core Security Principles

### A. Electron Process Isolation & Hardening
- **Context Isolation:** `contextIsolation: true` must remain enabled on all `BrowserWindow` instances.
- **Node Integration:** `nodeIntegration: false` must remain disabled.
- **Sandboxing:** `sandbox: true` must remain enabled.
- **Web Security:** `webSecurity: true` and `allowRunningInsecureContent: false`.
- **Navigation & Window Open:** All external window creation attempts are denied via `setWindowOpenHandler(() => ({ action: 'deny' }))`. Navigation is restricted to trusted origins.
- **Content Security Policy (CSP):** Strict CSP headers prevent inline script injection and remote resource execution.

### B. IPC Validation & Sanitization
- All incoming IPC requests must be validated using Zod schemas from `@medidesk/validation`.
- Handlers catch domain errors and return structured `IPCResponse<T>` payloads. Internal stack traces and raw error messages are stripped in production.

### C. Role-Based Access Control (RBAC) & Authority Separation
- **`OWNER`:** Has administrative authority over organization profile, user lifecycle, role assignment, audit logs, licensing, and disaster recovery database restores.
- **`DEVELOPER` Isolation:** Developers possess technical authority (migrations, diagnostics, local backup) but have **NO DEFAULT ACCESS** to:
  - Patient demographics & medical records
  - Doctor profiles & consultation notes
  - Clinical visit records & diagnoses
  - Electronic prescriptions
  - Pharmacy inventory, batches, suppliers, and purchase orders
  - POS sales, returns, and financial reports
- **No `SUPER_ADMIN`:** The codebase contains no universal backdoor or bypass role.
- **Last-Active-Owner Invariant:** The application forbids deleting or deactivating the last remaining active Owner account.

### D. Zero-Trust Cryptographic LAN Transport
- **TLS 1.3:** Self-signed certificates generated dynamically per clinic instance with SHA-256 certificate fingerprint pinning.
- **6-Digit Pairing PIN:** Ephemeral (10-minute expiry), single-use PIN generated by Owner.
- **Owner Approval:** Workstations register in `PENDING_APPROVAL` status and cannot access APIs until explicitly approved.
- **HMAC-SHA256 Request Signing:** Every request includes `X-Device-Id`, `X-Device-Signature`, `X-Request-Timestamp`, and `X-Request-Nonce`.
- **Replay Protection:** Freshness window of $\pm 300\text{s}$ and in-memory nonce cache.
- **Device Revocation:** Immediate server-side invalidation.

### E. Hybrid Backup & Restore Security
- **Encryption Algorithm:** AES-256-GCM authenticated encryption with 256-bit key derived via `scrypt` (`N=32768, r=8, p=1`).
- **Encrypted Header:** `MEDIDESK_ENC_V1` header with random 16-byte salt and 12-byte GCM initialization vector (IV).
- **Integrity Validation:** SHA-256 sidecar checksum and 16-byte GCM authentication tag verification.
- **Restore Safety Snapshot:** Automatic `PRE_RESTORE_SAFETY` backup created before database replacement.

### F. Password Hashing & Secret Management
- Passwords are hashed using Scrypt with cryptographically random 16-byte salts.
- Plaintext passwords and API secrets are never logged, persisted in audit logs, or returned in API responses.

## 2. Mandatory "NEVER DO THESE" Rules

AI agents working on MediDesk must **NEVER**:

1. **NEVER** expose raw SQLite database files to network shares (SMB/NFS) or allow multiple Electron clients direct file access.
2. **NEVER** create raw SQL IPC channels (e.g. `executeSQL`, `runQuery`, `rawSql`).
3. **NEVER** create shell/command execution IPC channels (e.g. `runCommand`, `exec`, `spawn`).
4. **NEVER** expose Node.js APIs (`fs`, `path`, `child_process`, `crypto`) directly to the renderer.
5. **NEVER** hardcode cryptographic keys, Google Drive client secrets, or user passwords in source code.
6. **NEVER** disable security controls, CSP, or context isolation to fix build or test failures.
7. **NEVER** grant Developer role default access to clinical, patient, prescription, pharmacy, or financial data.
8. **NEVER** rely exclusively on UI-level permission checks; always enforce RBAC in application/domain services.
9. **NEVER** destructively edit or delete released database migration scripts (`001` through `007`).
10. **NEVER** transmit unencrypted SQLite databases over LAN or to cloud storage providers.
