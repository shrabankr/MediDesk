# MediDesk LAN & Multi-Computer Technical Architecture

## 1. System Overview
MediDesk LAN Mode enables multiple workstations across a clinic or pharmacy to operate simultaneously on a single shared database without requiring an active Internet connection.

```
[ Doctor PC (Client) ]     [ Pharmacy POS (Client) ]     [ Reception (Client) ]
          │                           │                            │
          └───────────────────────────┼────────────────────────────┘
                                      │
                   HTTPS / WSS Transport (Port 4848)
                Pinned Certificate + Device Token Signing
                                      │
                         ┌────────────▼────────────┐
                         │  MediDesk LAN Server    │
                         │ ─────────────────────── │
                         │ • Fastify API Host      │
                         │ • Server-Side RBAC      │
                         │ • Serialized Mutex Tx   │
                         │ • Authoritative SQLite  │
                         │ • Hybrid Backup Engine  │
                         └─────────────────────────┘
```

## 2. Security & Zero-Trust Verification
- **Pairing Protocol:** 6-digit cryptographic PIN generated by the Owner on the Server PC. Single-use and expires in 10 minutes.
- **Owner Approval:** Every client device is registered in `PENDING_APPROVAL` status until explicitly approved by the clinic Owner.
- **Request Signing & Replay Protection:** Every request contains `X-Device-Id`, `X-Device-Signature` (HMAC-SHA256), `X-Request-Timestamp` ($\pm 300\text{s}$), and `X-Request-Nonce`.
- **Instant Revocation:** Revoking a device immediately invalidates all active sessions from that workstation.

## 3. Concurrency & Stock Allocation Guarantees
- **Atomic Serialization:** POS billing and stock allocations execute inside serialized transactions with `BEGIN IMMEDIATE` locking.
- **Zero Negative Stock:** Simultaneous sale requests on the same batch are processed sequentially. If stock is exhausted by the first client, the second request fails cleanly with an `InsufficientStockError`.

## 4. Failure & Recovery Invariants
- **Server Shutdown:** Clients detect lost heartbeat ($< 3\text{s}$), enter `DISCONNECTED` state with graceful exponential backoff, and automatically resume once the server restarts.
- **No Conflicting Offline Writes:** To guarantee complete ledger integrity, clients never accept uncoordinated local offline writes.
